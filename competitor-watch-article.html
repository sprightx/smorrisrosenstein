Your competitive intel is probably stale. Here's how I built a system that tells me when.

Every B2B marketing team has the same artifact: a competitive matrix that was excellent the week someone wrote it. It's deep and well sourced, the sales team trusts it, and then it quietly rots. No one wants to own the process of keeping it up to date, because doing so by hand takes forever and it's not fun work.

Now, you would think “AI can do this for me”, and the answer is yes, it can, but there is a wrong way and right way to do it.

To solve this, I built a competitor watch system that always delivers exact outputs. It runs in Claude Code, and the part I'm proudest of is how little of it depends on the LLM making judgement calls.

The design principle: deterministic detection, AI interpretation

The impulse most teams will have is to ask an LLM to write a competitive brief about a competitor and then, periodically, to go back to their website and recheck everything and update the document with whatever is new. This is the wrong way to do it. Working this way, you're asking the LLM to make way too many judgment calls.

Your outputs will look good, but every time you re-run the process the model will make small changes that you didn't account for and won't notice, and slowly your structure and content will start to drift. After many runs, your matrices for each competitor will be different from each other, and you'll find you're missing information that is important.

I split the system into four layers with a hard line through the middle:

  1. Crawl and diff. Python, no LLM. The same input always produces the same output.
  2. Materiality gate. Python, no LLM. A closed rule set assigns every change a tier.
  3. Analysis. Claude, working from a small, structured packet.
  4. Delivery. A Google Doc report, updated matrices, and state committed to git.

Everything above the line decides what changed. Claude only decides what it means. That boundary is the whole point.

The orchestrator: a Claude Code skill

The entry point is a Claude Code skill: I type /competitor-watch and the run begins. The skill file itself is deliberately thin. It points to a procedure document kept in version control, so every run follows exactly the same steps, wherever it's launched from.

That procedure walks Claude through eight steps:

  1. Run the scan (a Python command).
  2. Read the change packet the scan produced.
  3. Load our own positioning: the competitive matrix and battle card for each competitor with a material change.
  4. Produce one structured finding per material change.
  5. Write the analysis back into the packet, then draft edits to the affected matrices.
  6. Render the report and publish it.
  7. Send any drafted change to sales guidance through an expert review pass.
  8. Show me every edit as a before and after. I approve, amend or drop each one, and only then does Claude apply it and republish.

The skill handles the orchestration: running scripts, reading files, reasoning about impact, drafting edits and publishing. The scripts handle everything that needs to be repeatable.

The Python layer: where the real work happens

The crawler is plain Python, standard library only, so it runs anywhere without a dependency install. Per competitor, it:

  • Finds pages through the sitemap that robots.txt declares, falling back to common sitemap paths when that one is stale.
  • Harvests links from hub pages, because a sitemap is a floor, not a ceiling. We found a live customer story that wasn't in its sitemap.
  • Fetches politely. It respects robots.txt, sends one request every 1.5 seconds per host, and never goes behind a login or a form.
  • Extracts and normalises the text, stripping navigation, footers and cookie banners, then hashes it.
  • Diffs each page against the stored text from the last run.
  • Sweeps every page for tripwires. These are regex patterns seeded from the “monitoring triggers” in our own matrices. Has this competitor published a compliance claim? Entered our vertical? Launched a pricing page?

Then the materiality gate tiers every change by rules, not vibes:

  • T1: a critical tripwire firing for the first time, a URL that used to 404 now resolving, or a new product or pricing page.
  • T2: a metadata change on a watched page, a new case study, or a heavy rewrite of a key page.
  • T3: routine content, such as a new blog post, listed in the appendix.
  • T0: noise, dropped and counted.

Only T1 and T2 reach Claude. That keeps the model's input small, which keeps both cost and variance down.

Structured outputs: how I pinned the LLM's shape

Even in the analysis layer, Claude isn't writing free-form prose. Every finding is a structured object with constrained fields:

  • Classification comes from a closed list of eleven values: product-launch, capability-added, messaging-shift, proof-added, compliance-posture-change and so on.
  • Impact is HIGH, MEDIUM or LOW, against a written rubric. HIGH means the change closes a gap we currently exploit or invalidates a sales counter-message.
  • Action also comes from a closed list: update the matrix, update the battle card, brief sales, request research, or no action.
  • Invalidates names the exact claim in our own material that just went stale.

The wording varies from run to run. Which items surface, and how they're rated, does not.

The competitive matrices themselves are now YAML claim stores. Every claim has an ID, a section, an as-of date, a status and a source. The human-readable matrix and the published Confluence page are generated from the YAML. Nobody edits them by hand, and a check fails if anyone does.

When the crawl finds that a claim is stale, Claude doesn't rewrite a paragraph. It drafts a batch of typed operations: replace_text on a specific claim ID, trigger_fired on a monitoring trigger, flag_stale on anything that needs more research. A Python CLI validates and previews the batch before anything touches the source. So an AI-suggested change can be diffed, reviewed and reversed, like any code change.

Humans stay in the loop where it matters

  • Edits wait for approval. I approve every matrix edit in the session. Battle cards stay flag-only: the system names the stale line and recommends a fix, and a person makes the change.
  • Sales guidance gets expert review. Any change to sales-facing guidance goes through a domain-expert review agent first.
  • Absence claims carry a date. The report never says “they don't have X.” It says “X is absent from the 407 pages crawled on 10 September.”
  • Unseen means unseen. If a site blocked us, the Run Health section says that competitor wasn't seen this run. It never implies nothing changed.

The test that makes it trustworthy

The acceptance test is simple. Run two scans back to back against unchanged sites, and the system must report zero changes. We're at 99.96% stable across about 2,500 pages. The one offender is a page that genuinely renders differently from one fetch to the next.

Getting there taught me things you can't guess in advance:

  • lastmod dates are useless. CMS-wide republishes stamp hundreds of pages with the same date, so content hashing is the only honest signal.
  • Noise filtering can eat whole pages. One site wraps every content block in a class we'd flagged as chrome, and its homepage extracted to 25 characters.
  • Tripwires cry wolf. “CSV” means comma-separated values far more often than computer system validation, and “CMO” can be Contract Manufacturing Organization or Chief Marketing Officer. Prefer a pattern that misses a soft mention over one that fires on noise.
  • A run that can't see a site must not touch that site's state. A blocked crawl once looked exactly like a competitor deleting its entire website.

Where to start

You don't need all of this on day one. Start with:

  1. A registry of competitors, their domains and the pages you care most about.
  2. A Python crawl-and-diff script that stores normalised text and hashes in git.
  3. A handful of tripwires taken from your own battle cards' “if they ever do X, our message breaks” list.
  4. A Claude Code skill that runs the script, reads the diff, and writes findings in a fixed schema.

Run it two or three times and tune the noise rules before you trust it. Then move your matrices into structured YAML, so the system can tell you exactly which sentence just went stale.

The value of this system isn't the changelog. It's the one sentence that tells a sales rep their counter-message stopped working this morning.
